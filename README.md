# CAN monitor

Веб-панель мониторинга накопителя энергии (НЭ) и его устройств по шине CAN.
Читает обе шины, CAN1 и CAN2, через два USB-CAN адаптера SLCAN, разбирает кадры по карте
сигналов из репозитория `ESMS CAN map` (формат mapcan v2) и показывает в
браузере. Сделана на
[NiceGUI](https://nicegui.io/), оформление — в стиле
[btop](https://github.com/aristocratos/btop).

## Что показывает панель

- источник данных: порты и скорость, состояние CAN1 и CAN2 (`подключен` с числом кадров в секунду или `отключен`) либо имитация;
- состояние НЭ: общее состояние, состояние БУНЭ, предупреждения, ошибки;
- прокручиваемую таблицу устройств шины (БУНЭ, ПУЭР, СКИ, БУП, КК, БУСТ-А, БУСТ-Б, ПЛОД): состояние, link (интервал между двумя последними выходами устройства на связь по любой шине в мс, `×` при потере связи), число аварий и предупреждений (названия в подсказке), NMT-состояние, Node-ID;
- заряд (SoC), ресурс (SoH), допустимые токи заряда и разряда;
- напряжение, ток, среднюю, минимальную и максимальную температуру накопителя (5 датчиков кадра `storage_t_cc`);
- преобразователь (БУП): состояние, фактический и запрошенный режим, уставку, напряжения и токи сторон шины и накопителя, флаги;
- команды контакторов (обратной связи нет; команда К2 идёт через ПУЭР, К1 БУНЭ коммутирует напрямую и в CAN его команды нет), изоляцию (R+, R−, напряжение) и систему охлаждения: слева уставка и шесть вентиляторов БУСТ-А, справа уставка и обратная связь вентилятора преобразователя (Вент ППН) и шибер БУСТ-Б;
- карту ячеек: 68 напряжений групп и 102 температуры сеткой цветных плиток: группы нумеруются с 0; на вкладке температур — все датчики, от которых есть данные, с температурой на плитке, адрес `шина.номер` в подсказке, у датчиков с неизвестным ROM-кодом — «не привязан»;
- журнал событий (изменения состояний, события EMCY, подключение адаптера, введённые команды и их результат) и командную строку под ним.

Все значения обновляются на лету.

Кадры шины 2 (`status_bune`, `limits_bune`) разбираются, если адаптер подключён к шине 2.
Отдельных адаптеров для шины 2 и передачи команды `command_monitor` в БУНЭ пока нет.

## Запуск

```
pip install -r requirements.txt
python app/main.py
```

Панель откроется по адресу `http://localhost:8080`.

| Команда                            | Что делает                                                 |
|------------------------------------|------------------------------------------------------------|
| `python app/main.py`               | читает обе шины с адаптеров, порты из `config/settings.yaml` |
| `python app/main.py --port COM5 --reserve-port COM6` | то же, но с другими COM-портами |
| `python app/main.py --debug`       | без адаптера: все параметры имитируют работу системы       |

Если порт не открывается (адаптер не подключён, порт занят), в секторе can
у этой шины горит `отключен`, причина пишется в журнал, а подключение повторяется
каждые несколько секунд. Как только адаптер появится, данные пойдут сами.
Шины работают независимо: панель показывает данные и с одним адаптером.

### Режим отладки (`--debug`)

Преобразователь по кругу проходит режимы (предзаряд, ожидание, заряд,
разряд). За ним меняются SoC, напряжения, токи, напряжения групп и
температуры, производительность охлаждения и шибер, команда К2. Изредка
возникают и сами проходят неисправности: низкая изоляция, перенапряжение
стороны накопителя, потеря датчика температуры, потеря CAN2. В секторе can у обеих шин
горит `имитация`.

## Настройки

Всё, что может понадобиться поменять, лежит в `config/`. Изменения
применяются после перезапуска панели.

| Файл                   | Что в нём                                                                 |
|------------------------|---------------------------------------------------------------------------|
| `config/settings.yaml` | COM-порт и скорости адаптера, путь к карте CAN (`can.map_file`), порт веб-страницы, пороги цветов, таймауты связи устройств, размеры карты ячеек, журнал |
| `config/pattern.yaml`  | раскладка панели: сетка, какой сектор где, заголовки и цвета рамок         |
| `config/commands.yaml` | команды оператора для командной строки (пока пусто, формат описан в файле) |

### Команды

Встроенные команды панели (кадров в шину не шлют):

| Команда                       | Что делает                                                          |
|-------------------------------|---------------------------------------------------------------------|
| `/ports`                      | список активных COM-портов в журнале                                |
| `/connect COM5 250000`        | подключить адаптер CAN1 к порту, скорость общая для обеих шин (можно `250k`; без скорости — текущая) |
| `/disconnect`                 | отключить оба адаптера                                              |

При открытии командной строки для каждого найденного COM-порта сразу
предлагается готовая строка `/connect <порт> <скорость>`. Допустимые
скорости SLCAN: 10k, 20k, 50k, 83.3k, 100k, 125k, 250k, 500k, 750k, 1000k.
В режиме `--debug` адаптера нет, и `/connect` не работает.

Кроме них командная строка предлагает команды из `config/commands.yaml`. У каждой
команды есть имя (то, что вводится в строке), описание, CAN ID кадра и
значения его параметров; раскладка байтов этого кадра описывается в
карте CAN, как и у принимаемых кадров. Сейчас команд нет, а
отправка кадров ещё не реализована: введённый текст попадает в журнал с
пометкой `unknown command` (или `sending is not implemented yet` для
описанной команды).

### Как данные попадают на панель

`PARAMETERS` (`app/parameters.py`) разложен по устройствам шины 1: `bune`
(БУНЭ), `puer` (ПУЭР), `imd` (СКИ), `bup` (БУП), `cc` (КК),
`bust_a` (БУСТ-А), `bust_b` (БУСТ-Б), `plod` (ПЛОД). Отдельно `bus` — состояние адаптеров обеих шин. Список значений
каждого устройства берётся из карты. Флаги хранятся как `fault.u_dc_high`,
команды БУНЭ устройству — с приставкой `cmd.`.

`canbus/reader.py` получает кадр, `protocol.decode()` разбирает его по
карте, и значения кладутся в `PARAMETERS[устройство]`. Кадры `array_cc_v` и
`array_cc_t` раскладываются по массивам `cell_voltages` и `cell_temperatures`
(по два значения в кадре). Температура попадает на место по шине 1-Wire и
номеру датчика. Датчики с неизвестным ROM-кодом хранятся отдельно
(`free_temperatures`) и показываются вместе со всеми как «не привязан». События EMCY идут в журнал.

Каждая шина проверяется отдельно. Кадр с неверным DLC, CRC или повтором CNT на
этой шине отбрасывается и таймаут не продлевает. У устройства пропадает link на
шине при таймауте любого его кадра или после `can.invalid_limit` недостоверных
кадров подряд. Вернётся link только после `can.restore_count` достоверных кадров подряд, у каждого CNT
на 1 больше предыдущего (документ 03, REQ-1-8). Потеря связи на одной шине — предупреждение, на обеих — состояние
`NONE`. Копия кадра со второй шины новым выходом на связь не считается. Значения кадра, который перестал приходить по обеим шинам, сбрасываются в
`—`. `summary.py` выводит из значений состояния устройств и НЭ. Имитатор пишет в те же `PARAMETERS`,
поэтому панель не знает, откуда пришли данные.

## Отправка тестовых кадров через адаптер

```
python tools/can_sender.py --port COM7 [--bitrate 250000] [--verbose]
```

Шлёт в шину через адаптер SLCAN периодические кадры устройств из карты,
включая массивы ячеек, с настоящими CNT и CRC. Команды БУНЭ устройствам не
отправляются. Значения берутся из имитатора (`app/simulation`),
кадры собираются функцией `protocol.encode()` — обратной к разбору. Так
проверяется вся цепочка: адаптер → шина CAN → второй адаптер (или BUNEcan)
→ дашборд на его порту (`python app/main.py --port COM6`).

## Требования

- Python 3.10+
- зависимости из `requirements.txt` (NiceGUI, python-can, pyserial, PyYAML)
- два USB-CAN адаптера с протоколом SLCAN (CANable, USBtin, Lawicel и т. п.), по одному на шину
